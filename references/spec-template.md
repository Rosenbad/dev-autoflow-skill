# 需求规格契约（Phase 1 必读）

把用户的原始需求压成**固定字段的结构化规格**。契约的目的是：字段齐了才能开工，验收可测了才能交付。写完后必须运行 `scripts/spec_check.py` 校验。

## 字段契约

规格必须包含以下字段，**每个字段都有硬性要求**：

```
【目标】一句话：交付什么、解决什么问题
【受众/使用场景】谁用、在什么场景用
【交付形态】网页 / 脚本 / 表格 / 文档 / PPT / 报告 / 工程代码...
【核心功能】编号列出 3~8 条，每条一句话
【范围边界】明确"不做"的排除项（防过度开发）
【技术约束】用户点名或默认的技术栈/平台/限制
【验收标准】编号列出，与核心功能一一对应
【成本预算】规模估计：文件数/数据量/页面数；标注"小而快"或"需分阶段"
【待确认项】本次采用的默认假设清单（用户可随时推翻）
```

## 硬性要求（脚本会检查）

1. **九个字段一个不能少**——缺字段 = 规格没定稿。
2. **验收标准条数 ≥ 核心功能条数**——每条功能都对应一条"怎样算完成"。
3. **验收标准必须可测**——含可验证动词：能打开/能运行/能刷新/显示/返回/输出/解析/通过/不超过/点击/切换等。写"体验要好"是无效验收；"页面 3 秒内打开且数据正确显示"才可测。
4. **范围边界必须含"不"**——没有排除项的规格会过度开发。

## 重构手法

- **剥离外壳**：剥掉"先出方案""我是资深 X""帮我做个平台"等包装，找最终交付物形态。
- **补全缺失**：用户只说"做什么"，不说"给谁、什么形态、边界、怎样算完"——缺失且影响方案才问（≤3 问）。
- **压缩冗余**：描述性语言压成可执行条目，不保留空话。
- **先探查再定稿**：需求依赖实时外部信息时，先搜索/读文件再写规格，禁止基于错误前提开工。

## 校验命令

```
python scripts/spec_check.py <规格文件>
```

退出码 0 → 进入 Phase 2；非 0 → 按输出补齐字段/改可测验收，直到通过。

## 示例（已通过 spec_check）

**原始需求**："帮我做个员工考勤的看板，要能看到迟到早退。"

**规格文件内容**：

```
【目标】做一个员工考勤可视化看板，展示迟到/早退/缺卡统计
【受众/使用场景】HR 专员在浏览器内查看
【交付形态】网页（按 channel-map 判定走 html 或 app-builder）
【核心功能】
1. 按员工维度展示迟到/早退/缺卡次数
2. 按部门/日期维度汇总统计
3. 支持日期范围筛选
【范围边界】不做打卡功能本身、不做审批流、不做移动端适配
【技术约束】未指定，默认纯前端
【验收标准】
1. 打开页面能显示考勤统计图表
2. 切换日期范围后数据能随之刷新
3. 数据来自用户提供的 CSV，解析无误且数字与源文件一致
【成本预算】单页小任务，直接执行
【待确认项】数据来源假设为用户提供的 CSV；若超 10 万行需提示分阶段
```
